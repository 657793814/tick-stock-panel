# tick-stock-panel 项目审查与分析报告

**重点方向**：第三方付费内容（第三方数据/积分、赞助/打赏、第三方组件许可、开放平台商业化）的现状盘点与改造机会/红线分析
**报告范围**：项目整体审查；第三方付费相关面为改造重点
**基线**：基于工作区 v0.3.37（git main @1d0b13c3 "Update README.md"）静态审查

## 0. 结论摘要（TL;DR）

1. **项目定位**：tick-stock-panel（TSP / TickFlow）是自托管、零外部数据库的 A 股智能量化工作台：核心能力开放为受控接口 + MCP，核心域 8、扩展域 5（可整体替换/移除）。MIT 许可，3000+ 测试全绿（约 100 秒），开放接口 ~65 端点（roadmap 记 68），12 个 MCP 工具，AI 助手 21 查询 + 5 动作，19 个页面。
2. **当前第三方付费现状（两代，项目自身不直接定价）**：
   - **数据侧**：付费能力 = 第三方 Key + 积分/档位，具体为 TickFlow 档位（none/free/starter/pro/expert）、通达信 TdxQuant 积分计费、fuyao 免费 Key；积分由上游消费，项目自身不做定价；档位探测（先探后存）控制付费档位接入。
   - **内容侧**：赞助商横幅 + 社区打赏（RunningHub、支付宝/微信赞赏码等），明确「MIT 永久免费、打赏不解锁功能、第三方数据源费用与本站无关」。
   - **开放能力侧**：面向本部署二开、默认内网门禁（API_TOKEN_LOCAL_ONLY），不是对外数据分发通道。
3. **改造必须先界定边界**：是「接入/盘活已有第三方付费内容」，还是「把自有能力做成付费内容/对外变现」，还是「把第三方数据/积分做合规化接入」。当前报告只做现状盘点与机会/红线分析，待确认边界后再细化方案。
4. **主要红线**（改造中必须遵守）：第三方代码同权、第三方数据再分发责任在部署者、未来 AGPL-3.0 + 商业双授权预置、第三方仿真禁止 iframe 同源部署、迁移必须经 target/classes + Flyway 并同步 migration-hashes.json、探针/精度/视口比例等既有约束。

## 1. 项目概览

- **定位**：A 股智能量化工作台（TickFlow 品牌），核心为量化研究、回测、因子、盘中信号、监控、异动、个股/连板等，能力开放为受控 API + MCP。
- **部署形态**：自托管、零外部数据库（数据以 Parquet + DuckDB 文件型存储）；Docker 单容器。
- **架构分层**：核心域（8）+ 扩展域（5），扩展可整体替换/移除；能力按路由矩阵分发，提供单一 enriched 口径与双通道（密码会话 + Token 网关）。
- **技术栈**：
  - 后端：Python 3.11 + FastAPI + Pydantic v2、Polars、DuckDB、vectorbt。
  - 前端：React 18 + Vite 6 + TypeScript + Tailwind、Lightweight Charts、ECharts、dnd-kit；19 个页面（11 个为单文件扩展）。
  - 交付：Docker 单容器；约 65 个开放端点（roadmap 记 68）、12 个 MCP 工具、AI 助手 21 查询 + 5 动作。
- **规模与许可**：MIT；约 3000 个测试全绿约 100 秒；文档含 README、CONTRIBUTING、docs/（features、configuration、extension-packages、custom-data-source、open-platform-plan、sponsors）、操作说明书等。

## 2. 项目结构与主要模块

- `backend/`：应用主程序、能力路由与扩展、数据源/插件、迁移（target/classes + Flyway）、依赖 extras。
- `front/`：React 前端、页面（设置页含 Keys/About 等）、单文件扩展、page-pack、第三方组件（轻量图表）。
- `mcp-server/`：MCP 工具定义与调用。
- `packaging/`、`scripts/`：构建与工具链脚本。
- `docs/`、`assets/`：文档、图标/二维码、第三方组件许可。
- `examples/`、`data/`：示例与数据源（含 `data/data_sources/*.yaml`）。

与付费相关的主要文件/位置（供后续改造定位）：
- `tiers.yaml`：TickFlow 套餐能力/限速对照（none/free/starter/pro/expert）。
- 数据源插件契约 `plugin.yaml`（如 tdxquant / fuyao）。
- 数据源实现：`app/tickflow/`（policy.py 档位探测、client.py 付费实时客户端）、`data_providers/custom/`、`backend/app/extensions`、`plugins/`。
- 自定义数据源：`data/data_sources/*.yaml`。
- 前端：`front/src/components/OssLicenseDialog.tsx`、`front/src/data/ossLicenses.ts`、`front/src/pages/settings/Keys.tsx`、`front/src/pages/settings/About.tsx`。
- 商业化资产：`README.md`（含赞助横幅/打赏）、`docs/sponsors/`、`assets/support/`。

## 3. 第三方（Third-party）相关面盘点（改造重点）

### 3.1 第三方数据源与付费能力

- **TickFlow（官方内置/主要付费源）**：
  - 套餐能力对照 `tiers.yaml`：none / free / starter / pro / expert，能力键含 kline.minute.batch、depth5.batch、financial、intraday 等，并标注 rpm/batch 限速。
  - 档位仅适用于 TickFlow 源；其他源按能力声明合并判定（tiers.yaml 注明 pricing 页为前端动态渲染、数值沿用 2026-05-21、部分条目为「推断」）。
  - 接入策略：None/free 走 free-api（仅历史日 K）；free 含自选实时（10 rpm / 5）；starter+ 走 api.tickflow.org 实时。
  - 档位探测：`app/tickflow/policy.py` 的 `detect_capabilities`（先探后存、防网络抖动误降级）；付费实时客户端 `app/tickflow/client.py` 的 `get_paid_realtime_client`。
  - 前端对应：设置页 Keys 提供 API Key 配置/保存并检测/清除，展示档位与能力矩阵联动失效。
- **fuyao（同花顺 REST，免费 Key）**：无 billing 声明，数据集 realtime / daily / adj_factor / financial，`API_KEY FUYAO_API_KEY`。
- **TdxQuant（通达信）**：`plugin.yaml` 契约 `billing: points`（积分计费，设置页能力芯片标注「积分」），`api_key_env TDXQUANT_API_KEY`，`key_manage_url` 指向通达信商城，数据集 realtime/depth5/daily/adj_factor/minute/full_minute，依赖已内置 tdxaidata DLL。
- **自定义数据源**（`data/data_sources/*.yaml`）：7 类数据集（daily/adj_factor/realtime/minute/depth5/full_minute/financial）；鉴权 3 种（bearer/header/query）；含 field_map / transforms / pct_unit；出站标识头 `User-Agent: tsp/<版本>; X-TSP-Client: tick-stock-panel`；用于定时拉取、CSV/JSON 写入等。
- 数据侧付费本质：**全部由第三方上游提供，项目自身无定价体系**，仅通过 Key + 档位/积分控制访问与能力。

### 3.2 第三方组件与许可

- 项目以 MIT 开源，但随应用分发第三方组件，需完整保留版权/许可声明。
- 第三方组件清单：前端组件、后端组件，`OssLicenseDialog.tsx` 展示 LICENSE 全文 + 清单（MIT 外组件徽标）；数据来自 `front/src/data/ossLicenses.ts`。
- 示例第三方组件：Lightweight Charts（Apache-2.0 + NOTICE）位于 `front/public/third-party/lightweight-charts`；About 页常驻第三方组件链接与许可说明。
- 界面合规声明常驻：`LicenseComplianceNotice`（许可合规声明，设置/关于页）、打赏页明确「MIT 永久免费、打赏不解锁功能、第三方数据源费用与本站无关」。

### 3.3 商业化 / 赞助 / 打赏 / 开放平台

- **赞助商内容**：README 顶部 `docs/sponsors/` 含 RunningHub 横幅（runninghub-banner、runninghub-banner-v2/v3、intro card、sponsor-header）与 modelflare banner 大图，以及 RunningHub 推广；资源在 `assets/support/`（支付宝、微信赞赏码、社区二维码等）。
- **打赏**：关于页打赏区块（完全自愿、不影响任何功能），引导微信赞赏；明确不解锁功能、第三方数据源费用与本站无关。
- **开放平台门户**：`tsp.shy313.com`，提供注册/邀请/创建 API Key/在线调用，与 `tiers.yaml` 的价格预估相关——是核心能力对外（付费转化）的潜在入口。
- **第三方插件/扩展计费**：插件契约 `billing: points`（积分），商城积分由上游平台消费。

### 3.4 扩展与第三方代码边界

- 扩展体系：`backend/app/extensions`、`data_providers/custom`、`plugins`；后端扩展包契约 `extension.yaml`；前端 `front/src/custom` 单文件扩展 + page-pack / 页面插件（运行时分发，免重建宿主）。
- **关键边界/风险**：页面插件任意代码同权、第三方代码沙箱不在 v1（即第三方代码与项目代码同权，无独立沙箱防护）；第三方仿真必须同源单 HTML、禁止 iframe。
- 其他合规/工程约束：开放接口默认仅本机/内网（`API_TOKEN_LOCAL_ONLY=1`）、管理面不开放 Token、CORS 白名单、SSE 60 秒票据；第三方数据再分发责任由部署者承担；迁移须经 `target/classes` + Flyway 并同步 `migration-hashes.json`。
- 未来授权预置：CONTRIBUTING §14 预置未来引入 AGPL-3.0 并可能提供商业许可（AGPL + 商业双授权），涉及分发第三方贡献代码时需相应再许可授权。

## 4. 第三方付费内容现状小结

- **数据侧**：付费 = 第三方 Key + 积分/档位（TickFlow 档位、TdxQuant 积分、fuyao Key），积分由上游消费，项目自身无定价；付费能力通过「先探后存」的档位探测接入，未构成独立付费产品体系。
- **内容侧**：付费 = 赞助商横幅 + 社区打赏，明确不解锁功能、与数据侧费用分离。
- **开放能力侧**：面向本部署二开、默认内网，是「受控接口/MCP + 开放平台」而非对外数据分发通道。
- 一句话：**当前项目第三方付费内容停留在「接入第三方付费能力 + 表面赞助/打赏」层面，尚未形成自己的付费内容与变现体系。**

## 5. 针对「第三方付费内容」的改造分析与建议

### 5.1 改造边界待确认（先明确方向）
1. **接入/盘活**：把现有第三方付费内容（TickFlow 档位、TdxQuant 积分、fuyao）接入得更完整、更可控？
2. **自有付费内容/对外变现**：把核心能力（回测、因子、盘中信号、数据面板等）做成付费内容或对外变现产品？
3. **合规化第三方数据/积分**：把第三方数据源、积分计费纳入更规范的计费/授权/合规体系？
请明确所选方向（或组合），再细化方案与验收。

### 5.2 现状机会点
- **付费能力已具备完整接入链路**：档位探测、能力路由、付费实时客户端、Key/档位管理界面均存在，接入改造重点是补齐「能力-收费-展示」一致性。
- **开放平台是潜在变现入口**：`tsp.shy313.com` 已有注册/邀请/Key/在线调用，可与 tiers.yaml 能力映射打通，形成「能力分级 + 购买/订阅 + 在线调用」的最小变现形态。
- **第三方积分可体系化**：tdxquant 等插件 `billing: points`，可沉淀统一的积分/能力计量与展示。
- **内容付费有既有资产但偏轻**：赞助横幅 + 打赏资产已就位，可升级为更结构化的赞助/订阅内容。
- **合规可加固**：许可清单、第三方组件徽标、MIT 再分发声明已建立，是商业化推进时的合规基础。

### 5.3 分阶段改造建议（建议）
- **阶段 0（确认边界）**：先确认改造方向（5.1），并核对 `tiers.yaml` 价格数值口径（前端动态渲染、部分为「推断」）与定价是否真实可落地。
- **阶段 1（接入与一致性）**：若方向为「接入/盘活」，补齐「能力键 ↔ 套餐档位 ↔ 限速/收费标签」的一致性映射；完善档位探测与失效联动（Keys 页已具备，需对齐数据源页）。
- **阶段 2（变现最小形态）**：若方向为「对外变现」，在开放平台门户 + 现有 Key/档位体系上，建立「能力分级 → 购买/订阅 → 在线调用」的最小闭环；优先只服务本部署/内网可控范围，遵循内网门禁。
- **阶段 3（合规与授权）**：无论是否对外变现，先把第三方数据/积分的授权与再分发责任、第三方代码边界（同权/无沙箱）明确并加防护约束；评估 AGPL-3.0 商业授权预置的影响。
- 全程遵循既有红线（见 5.4），并遵守 CONTRIBUTING 的 PR 复审、迁移 target/classes + Flyway、migration-hashes.json 同步等要求。

### 5.4 必须遵守的红线 / 合规清单
- 第三方代码同权：页面插件任意代码同权、第三方代码沙箱不在 v1，引入第三方代码时须评估并明确边界/防护。
- 数据再分发责任：第三方数据再分发责任由部署者承担，公开/对外分发第三方数据前须明确授权与合规。
- 第三方仿真：禁止 iframe 嵌入，采用同源单 HTML 方案。
- 迁移：经 `target/classes` + Flyway，同步 `migration-hashes.json`。
- 许可与再分发：MIT 分发须保留版权与许可声明；第三方组件需保留其许可文本（已在 OssLicenseDialog 建立）。
- 工程约束（沿用）：几何构造优先、探针内联与精度显式化、视口比例 1.875、探针/验证脚本校验、开放接口默认内网 + Token 网关、CORS 白名单 + SSE 票据等。
- 授权预置：注意未来 AGPL-3.0 + 商业双授权的引入可能带来的分发与商业授权影响。
